# 场景诉求陈述（v0 草稿）

> 2026-11-26，由 trace-viewer 定位讨论反推整理，待主人红线。
> 核心发现：这个 app 对我是**双重身份**，两类诉求都要成立，但节奏不同——分开记账，防止互相挤占。

## 场景

「个人助理（PA）」有两种身份：

1. **助理**（使用者 Sam 用它）：菜单栏常驻 + ⌥Space 浮窗，本机数据 + 长期记忆，日常帮我做事。
   现状：**尚未进入日常**——11 个会话 19 条消息，全是冒烟测试。
2. **试验田**（开发者 Sam 用它）：一套可复用的 agent harness（`AgentRunner` 循环 / 工具注册 /
   审批门控 / SQLite 记忆 / 轨迹）。新业务来了，目标是「改 harness + 改规则」就能接入，
   而不是从 0 起一个新项目。

## 我是谁

- 开发者 Sam：正在练 AI 工程 + AI 产品能力（见 `product/` 训练场），持续加工具、改 prompt 管线、上新场景
- 使用者 Sam：macOS 重度用户，手头已有多个 agent 型小业务（招聘对话、飞书操作、抖音下载、导购助手课题），目前都跑在 ZCode skills 上

## 现状与痛点

| 事情 | 现状 | 痛点 |
|---|---|---|
| 日常使用助理 | 冒烟测试为主 | 没有真实使用 → 没有真实事故 → 诉求缺证据 |
| 新业务接入 agent | 全部跑在 ZCode skills 上 | PA 能承接哪类业务还没定义 |
| 改 harness / 改规则 | 代码层有 mock-llm + 单测做回归；**行为层（prompt/规则）是盲调** | 改完 prompt 说不清变好还是变坏 |

## 诉求清单

**试验田身份（T）：**
- [ ] T1 最小评测闭环：攒轨迹 → 选金标准案例 → 改 harness/规则 → 重放对比 → 判定（详见 `testbed.md`）
- [ ] T2 完整跑通一次「新业务接入演练」，沉淀接入方法论：改哪些层、按什么顺序、每步怎么验证
- [ ] T3 仪器先于实验：轨迹数据层补保险（中间迭代拼装不覆盖，见 `trace-viewer.md`）

**助理身份（U）：**
- [ ] U1 让使用者 Sam 上班：每天真实使用，攒「被坑时刻」日记
- [ ] U2 从真实使用中提炼日常诉求（暂空，等 U1 的证据）

## 明确不想要什么

- 不做通用 eval 平台（LangSmith / Braintrust 那种），只做本机够用的最小闭环
- 不为试验田功能牺牲助理的硬指标（.app ≈ 2MB / 空闲 RSS ≈ 80MB / 零第三方依赖）

## 怎么算成了

- 下一个真实新业务来时：能在 PA 上以「改 harness + 改规则」方式接入，全程有轨迹与评测兜底
- 每次规则改动：有前后对比，能说出「变好 / 变坏 / 没差别」
- 使用者 Sam 有连续 14 天的真实使用记录
