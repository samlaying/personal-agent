# 专项诉求：轨迹分析（Trace Viewer）

> 2026-11-26 整理。图1 参考 = ZCode 的「轨迹」面板；图2 = 我们自己的聊天界面。
> 教练批注：最初表述是「我想做图1 那种轨迹分析」——那是**方案**。本文先把诉求还原出来，
> 形态（甘特条、双栏、tab）留到 PRD 阶段再对齐。

## 场景

agent 应用的行为由「模型看到了什么」决定，但聊天界面只展示「模型说了什么」。
每轮真正发出的请求 = `SystemPrompt.make(...)` + `TranscriptBuilder.trim(history)` + 工具结果，
这套拼装是纯手写逻辑（60k 字符预算、摘要复用、头部修复），而且**出错不报错**——
模型只是「变得怪怪的」。没有轨迹，排障全靠猜。

## 痛点（为什么要「看」）

- 「上下文哪里拼错了」在聊天 UI 里不可见；重发一遍、改改 prompt 再试，都是碰运气
- provider 400 只给一句报错，看不到违反了哪条拼装规则
- 模型引用了一条「我没写过」的规则时，无从知道它来自哪段注入

## 证据盘点（2026-11-26，只读查询 memory.sqlite）

| 指标 | 值 | 含义 |
|---|---|---|
| 轨迹轮数 | 6 | 全部来自今天 04:15–18:27，轨迹功能当天刚上线 |
| 出错 / 被拒轮数 | 0 | 「排障」还没有真实案例 |
| 每轮工具调用数 | 3 轮 0 次、3 轮 1 次 | 没出现过多步循环，A2 的盲区还没人踩进去 |
| 会话 / 消息 | 11 / 19 | 冒烟测试型使用（现在几点、列文件、hi），助理尚未进入日常 |

**结论：截至今天，「排障（A）」是框架推出来的假设，不是被事故验证的诉求。**
真正的驱动因素是两个未来事件：真实日常使用开始、多 agent 落地。

## 诉求清单（按四类 job 分层）

### A 排障（最高频）

- A1 出错轮次的真实拼装可查：system 分段 + 消息序列 + 每条来源（现状已有）
- A2 多步工具循环里，中间迭代的拼装不被覆盖
  （现状盲区：`TraceRecorder.setPrompt` "final assembly wins"，只留最后一次）
- A3 轮次列表直接标出哪轮出错/被拒，不用逐个点开（现状 TraceSummary 无状态字段）
- A4 工具结果被截断后的真实形态可见

### B 验证（改 prompt 管线后的回归确认）

- B1 改 `SystemPrompt.make` / `TranscriptBuilder` 后，逐块核对：注入了哪些段、每段字数、消息从 seq 几开始（现状已有）
- B2 消息正文目前只存尾部 4000 字（`suffix(cap)`），看不到长工具结果的开头

### C 理解（行为归因）

- C1 「模型为什么这么答」能下钻到具体哪段注入影响了它（现状：来源 + 裁剪规则卡已有，比图1 还细）

### D 优化（性能 / 预算）

- D1 会话级跨轮时间线：时间花在模型 / 工具 / 摘要哪一段（现状只有单轮纵向链路）
- D2 每轮预算使用：总字符、裁掉多少、摘要前后对比（现状只有汇总数字，无趋势）

## 明确不想要什么

- 不做云端 / 团队共享的 trace 平台（本机自用）
- 不做全量请求体录制：4000 字预览 + 按需看全文已够，全量存储的体积与写库成本不值
- 不做 A-B 评估、数据集回放这类「平台级」功能

## 怎么算成了

- 「模型忘了规则」类问题：5 分钟内定位到是裁剪丢段还是 prompt 本身没写
- provider 400：不开抓包，轨迹里直接看到违反了哪条头部规则
- 改完 `TranscriptBuilder`：连续看 3 轮轨迹确认新拼装，不再需要打日志

## 定位讨论（进行中，2026-11-26）

~~A2 / A3 最疼~~ ← 框架推演，已被上面的证据推翻一半。三个候选定位：

- **保险单**：趁 `TraceRecorder` 还新，把中间迭代的拼装记下来（`setPrompt` 覆盖 → 按迭代追加，数据层小改动、不动 UI）；多 agent 落地前先买上
- **教学可视化**：如果做这个 app 的目的包含「练 agent 工程」，轨迹本身就是学习材料，按教学需求设计（比如给每轮标注「摘要压掉了什么」），而不是按排障工装设计
- **等待模式**：不新增任何东西；第一次真实故障发生时，看现有 TraceView 够不够回答，缺的那块才是真需求
